# セッション同士のメッセージと MCPの経緯

なぜ今の形になったか（前はどうだったか・実測・レビューの指摘）。仕組みは [internals/agents.md](../internals/agents.md)。新しい経緯はこのファイルの該当する節に足す。

## セッション同士のメッセージ

### エージェント用の口を別の鍵にした

- 口は画面の返信とは逆で、`Origin` / `Sec-Fetch-Site` が付いていれば断り、`agent-token` の中身を要る。
- 同じマシンの CLI からループバックで叩くと Origin が無いので同一オリジンの検査は素通りするため、それとは別の鍵にした。
- MCP サーバには中身ではなく場所を渡す（`--mcp-config` は引数なので ps で見える）。

### 見出しに id を入れた

- record.py が `user_text` を 2000 字で切るので、本文の一致ではどのターンか決められないため（書いた当時の上限。いまの上限は 20000 字。#358）。

### 記録をファイルに残した（#440）

- 前はメモリだけで、立て直すと `sai_wait` が見失い、「送信を止める」が外れ、回数と予算が 0 から数え直しだった。いまは `agent-messages.json` に送った記録・止めたこと・1 ターンの回数と量・連鎖の印を書き、止めたことも同じファイルに残る。

### `sai_sessions` に「同じファイル」を出し、ツールの説明を「使う場面」から書いた（#564）

- 9 月の記録（2026-09-30）で、エージェントが `sai_send` を呼んだのは transcript 50 本で 2 回、エージェント発で回ったターンは 1 回だった。制限に当たって断られた形跡は無く、**そもそも送ろうとしていなかった**。
- 理由は 2 つ: いつ別のセッションに聞くかが決まっていなかった（きっかけが無い）、`sai_send` の説明が回数の上限・断られる条件・トークンの注意ばかりで、どんなときに使うかが 1 つも書かれていなかった（「使うな」と読める）。
- 一方、9/16 以降にマージした PR 90 本のうち 53 本（58%）が、同時に開いていた別の PR と同じソースファイルを触っていた（`server/app.ts` 37 組・`web/src/styles.css` 17 組・`shared/types.ts` 16 組）。誰も声を掛けず、コンフリクトしてから直していた。
- そこで重なりを材料として見せ、説明は使う場面を先に・制限を後ろに回した。**自動では送らない**（重なりの多くは `app.ts` に別々の関数を足すだけで、聞く必要が無い）。既存の歯止め（1 ターン 3 回・読み直す量の予算・相手の使用率）はそのまま。
- 効いたかは、エージェント発のターン（`【SAI】` で始まる行）の週あたりの数と、その費用（`turn-usage.jsonl`。#388 の材料）で見る。

### 送り元が待たなかった返答を画面に出した（#588）

- 2026-10-01 01:18〜01:56 に、Manager 役の `sai_main` が「〇〇のセッションで #N 着手」を 6 回送り、**6 回とも送った直後にターンを終えた**（`sai_wait` を呼ばず、返答の末尾は「返答は待っていません」）。受け取った側はどれも返答していた（例: dev-worktree-b は 01:40:22 に「着手・PR #584・詰まった点」）が、返答を送り元に運ぶ口は `sai_wait` しか無く、送り元の会話は「頼みました」で止まって「返事がないまま放置」に見えた。
- 着手は数十分かかり、Manager はその間に次の依頼を受けたいので、`sai_wait` でターンを握るのは合わない。**待たないのがふつうの使い方**と見て、返答を送り元の画面に並べることにした（トークンを使わず、記録も触らない）。
- 見出しの「このターンの最後の発言が送り元に返ります」は、待たない送り元には嘘になっていたので言い換えた。`sai_send` の説明にも「待たなければ返答は画面にだけ出る」を足した。

### 返答のバブルから相手へ返信できるようにした（#700）

- 2026-10-05 の実測（`sai_main` の画面に出ている直近 7 日の返答 20 件）で、**20 件とも**そのあと人が相手のセッションへ移って直接入力していた。入力は 17 件が「マージして」、返答が届いてから入力までの中央値は 4 分。返答を読む → リンクで相手へ移る → 打つ → 戻る、を毎回やっていた。
- 送り元のエージェントに送らせる（`sai_send`）形は採らなかった。送り元のターンが 1 回増え、文脈を読み直す（#624）。人が直接送る形は、いま手でやっていることと同じ。
- 送ったことを自分のバブルにしなかったのは、送り元のセッションに打った入力ではないため（送り元の会話に入ったように見える）。小さい 1 行にした。
- 相手の返答を「次のターン完了」でなく入力の頭で当てるのは、相手が処理中のときは預かりに並び、間に前のターンが終わるため。入力が記録に載らないターンには当たらないのは分かって残した（当て違えるより、出さないほうを選んだ）。
- 相手のセッションを一覧（`peers`）から引かず詳細の応答に載せたのは、一覧と詳細は別のポーリングなので、「返信が終わったのに行が増えていない」（`ENDED_WITHOUT_ROW`）を取り違えるため。
- 狭い画面で要対応のようにリンクへ落とさなかったのは、携帯ではこの 1 押し（「マージして」）が一番効くため（issue の「決めたこと」）。
- レビューの指摘で直した 4 つ: 相手への返信を確認から送り直すと、全体の数（`confirmedSent`）を見ていた送り元自身の入力欄まで空になった → 返信先ごとの数に。相手に未渡しの返答があると SAI が本文の頭に塊を足すので、入力の頭が一致せず返答が当たらなかった → 塊を外して比べる。繋ぎの 1 行を時刻（5 秒の幅）で消していたので、携帯の時計がずれていると二重に出て消えなかった → 行の数で見る。送信失敗の案内が同じ相手の全部のバブルの下に出た → 送ったバブルの下だけ。

### 返答を送り元の会話に戻した（#594）

- #588 で返答は送り元の**画面**に並ぶようになったが、送り元の**エージェント**には渡っていなかった。10/1 までの実測で、送ったメッセージ 10 件・返答 8 件（1 件 539〜2,060 字）のうち、送り元の会話に入った返答は 0 件、`sai_wait` を呼んだ回数も 0 回（`sai_send` 11 回に対して）。着手は数十分かかるので待たずに終えるのがふつうで、送り元は状況を聞かれるたびに `gh pr list` で調べ直していた。
- 決めたこと（10/1）: 既定は「次のターンの頭に添える」（ターンが増えない。増えるのは返答の字数ぶんだけ）。「回っていればその場で足す」は当たれば自動、「起こす」は送る側が選んだときだけ（後の PR）。起こされたターンからは送れないまま（連鎖 1 段。#311）。記録の `user_text` はそのまま、画面で外して見せる。端末で直接続けたときは未渡しのまま残す。
- 上限の数字: 8 件・合計 12,000 字（実データで 8 件の返答が 1 万字前後）・7 日（何日も前の依頼の返答を、関係の無い次のターンに混ぜない）。入りきらない分を名前だけの 1 行にして「渡した」にするのは、同じ返答が次のターンにもまた足されて頭が毎回膨らむのを避けるため（本文は相手のセッションと画面の返答のバブルで読める）。

### その場で足す・起こす（#594 の 2・3）

- 「次のターンの頭に添える」だけだと、複数に頼んで自分も作業を続けるターンでは返答が次のターンまで届かず、質問（「どこを変えますか」）は人が次を送るまで止まる。そこで、回っている送り元には入力の口から足し、送る側が選んだときだけ起こす。
- 起こすのを既定にしないのは費用のため: 送り元が 50 万トークンなら 1 回起こすごとに 50 万の読み直し。**同じターンで `wake` を付けたものはまとめて 1 回**にした（8 件を 1 件ずつ起こせば 400 万、まとめれば 50 万）。
- 起こしたターンから送れないのは今の決まり（メッセージで始まったターンからは送れない）のまま。返答を受けて次の依頼を出すには、人が次を送る。
- 起こすときの読み直しの量は、送る側のターンの予算（`AGENT_TURN_READ_BUDGET`）には数えていない（送ったターンはもう終わっている）。見ているのは使用量の枠と、人の「送信を止める」だけ。

### メッセージで頼んだ着手は要約されていなかった（#624）

- 画面からの「着手して」は要約してから始まる（#579 / #590）のに、`sai_send` の道は `launch()` に `compact` を渡しておらず、そのまま始まっていた。10/1 にメッセージで着手した 3 ターンは、1 回の呼び出しあたり 54〜82 万トークン（相手の文脈の大きさそのまま）を読んでいた。
- 判定は緩めなかった（`startsNewWork()` は 1 行目が着手の形で**終わっている**ときだけ）。それまでの依頼文は 1 行目に続きを書いていたので当たらない。送る側を合わせることにして、ツールの説明に「1 行目を『#N に着手してください。』だけに」を足し、取りこぼし用に `compact` の指定を残した。
- `/compact` に添える指示を見出し付きの本文から作ると「次は『【SAI】…からのメッセージです』に取りかかる」になるので、送り元が書いた文を `compactFrom` で別に渡す。
- Issue のテストの項には「要約が失敗したら本文をそのまま回す」とあったが、画面からの送信は本文を回さずに預かりを止める（#579）。そちらに揃えた（送り元には失敗と返る）。

### 宛先を呼び名でも書けるようにした（#625）

- `sai_send` の `to` は id しか受けず、取り次ぐセッションは呼び名から id を引くためだけに `sai_sessions` を呼んでいた。取り次ぎ 9 ターン（9/30〜10/1）の往復は中央値 4 回で、うち 1 回がこれ（1 往復あたり約 65 万トークン）。
- 一致は完全一致だけにした（「セッション B」と「セッション B - 別件」の取り違えを避ける）。表示名のあるセッションは題名では引かない（題名は最初の入力で、「着手して」のように他と重なりやすい）。
- 同じ worktree にセッションが 2 つ居る（`main`）と worktree 名では決まらない。そのときは送らずに候補を返す。
- 1 回で複数の相手に送る口は足していない（着手の依頼は相手ごとに文が違う）。

### 上限を超えた送信を預かるようにした（#727 の案 A）

- 2026-10-01〜10-07 の実測で、人の入力 268 回のうち 115 回（43%）が中身の無い取り次ぎだった。そのうち「残りも送って」の類は、1 ターン 3 回の上限（#311）で送り切れなかった分を人が打ち直していたもの（この 1 週間で 5 回）。
- 上限そのものは残した（その場で送れるのは 1 ターン 3 回・読み直し 300 万トークン）。変えたのは超えた分の扱いで、断らずに預かり、送り元のターンが終わってからサーバが順に送る。1 ターンの上限は「エージェントが止まらずに送り続ける」のを止めるためのものなので、代わりに**依頼 1 つの上限**（8 件・600 万トークン）を置き、預かる前に全部を数える。値は仮（#727 の「決めること 2」が決まっていない）。
- 巡の間を 60 秒空け、1 巡を 3 件にしたのは、預かりが一度に全部の相手を起こさないようにするため（人が画面で気づいて止める間を残す）。
- 止める口を増やさなかった（依頼の単位で止める口は作っていない）。いまの「送信を止める」が送り元ごとなので、預かりもそこで全部捨てる。
- 送りかけで立て直された 1 件を送り直さないのは、届いていた場合に相手のターンを二重に起こす（相手は長い会話を読み直す）ほうが、1 件を人に頼み直してもらうより高くつくため。忘れないように、理由を付けて画面に残す。
- レビューの指摘で直したもの: 送っている途中の例外で、送りかけの印が付いたまま誰にも送られず・捨てられもしない 1 件が残った（以後その送り元の送信が全部預かりに回る）→ 例外も含めて、送らなかった 1 件は理由を付けて止める。巡の途中に来たターンの終わりを取りこぼした・立て直したあと画面を開くまで動かなかった → 終わったあとにもう 1 回見る・起動のあとに見始める。1 件で 1 ターンの予算を超える相手が、預かりを通ると送れてしまった → 預かる前に断り、送る前にも見る。送る直前に送れなくなった分を黙って捨てていた → 止めて画面に残す。預かりを送った記録が、送り元の別のターンの回数を上書きした → 回数に足さない記録にした。ツールを並べて呼ぶと全部が「まだ 0 回」を見た → 送り元ごとに 1 つずつ通す。
- 入れていないもの: 自動で次の送信を決める・`wake` を既定にする（案 B）・マージを自動にする（案 C）。tailnet の `/mcp` からの送信は変えていない。

### `sai_sessions` に「いま持っているもの」を足した（#727 の案 D の読む側）

- 割り振り役が `sai_sessions` で分かるのは、最後の発言の 1 行とブランチ名だけだった。誰が空いているか・誰がどの issue と PR を持っているかは、最後の発言から推すしかなかった（「PR #N をマージしました」で終わっていれば空き、のように）。
- 持ち場を SAI が**書いて持つ**形（人やエージェントが「この issue はこの人」と登録する）は入れていない。登録を誰がしてよいか・割り振り役を決まったセッションにするか（#727 の「決めること 5」）が決まっていない。読むだけなら、今ある材料（ブランチ・open な PR・届けたメッセージの記録）から引ける。
- 当て推量で埋めないために、issue の番号はブランチ名の `issue-<番号>`・PR の題名・依頼の 1 行目だけから引く。最後の発言の本文からは引かない（「#12 は関係ありません」も拾ってしまう）。
- PR を待たずに返すのは、`gh pr list` が 1 回で数百ミリ秒〜数秒かかり、`sai_sessions` はエージェントのターンの中で呼ばれるため。前の結果を返して裏で引き直す。
- レビューの指摘で直したもの: 端末で人が回しているターンを「空き」と出していた（SAI が回しているものしか見ていなかった）→ transcript の上で動いているかも見る。失敗した・止められた依頼を 2 日間「頼まれ中」に数えていた → 相手の預かりに並んでいるか、相手が回しているものだけ数える。何時間も前に引いた PR の一覧を今の CI として出していた → 10 分より古ければ引いていないのと同じに扱う。依頼の `PR #N` や題名の括弧の外の番号を issue と呼んでいた → 行の頭の `#N`・`issue #N`・題名の括弧の中だけ。SAI が渡す口から端末と許可の走査を回していた（画面の走査の結果を、一部のセッションだけの結果で上書きしうる）→ 回さない。
- 頼まれて未完の依頼を 2 日で切るのは、返答の来なかった依頼（相手のターンが失敗した・人が止めた）をいつまでも数えないため。

### 別のリポジトリのセッションにも送れるようにした（#747）

- 同じ `project` に絞っていたのは、素通しのセッションに外から指示が入る範囲を狭めるためだった（#253 / #310）。並行して使うリポジトリが 3〜4 つあるのに、エージェント同士で頼めるのはその中の 1 つの中だけで、リポジトリをまたぐ口（`/manager`・`sai_suggest`）はどちらも人が間に入っていた。
- 人が決めたこと（2026-10-09）: またいだ先が素通しでも送れる（手元の主なセッションはほぼ素通しなので、断ると実質使えない）／別のリポジトリのセッションについて一覧に出すのは呼び名・エージェント・空いているか、まで（最後の発言を出すと、頼んでいない中身が毎回こちらの文脈に入る）／返答は今までどおり送り元に入れてよい（頼んだことへの答え）。受け入れたのは、送り元のエージェントが外から読んだ文に指示が混ざっていると、別のリポジトリの許可を聞かないエージェントまで届くこと。範囲は人が許した組で縛る。
- **組の持ち方は未決のまま、向きつき・一括の口なしで作った。** 向きを持たせたのは、仕事のリポジトリから個人のリポジトリへ頼むのと、その逆は流れる中身が違うため。一括で許す口を作らなかったのは、組を人が選ぶことが、素通しに送れるようにする条件だったため。双方向にするなら `mayCross()` の 1 行。
- 組を「記録で知っているリポジトリ」に限ったのは、任意の名前を持たせない（打ち間違い・まだ無いリポジトリへの先回りの許し）ため。
- 組を変えられるのは設定の口（同一オリジン）だけで、エージェント用の口と MCP の道具には道が無い。**ただし設定の口はブラウザの別オリジンを断るだけなので、手元でシェルを持つエージェントが `curl` で叩けば変えられる**（ほかの設定と同じ線）。ここを塞ぐには設定の口に別の鍵が要る。入れていない。
- `/manager` を送れるようにする件は、送れる範囲（許した組の中だけか、全部か）が決まっていないので入れていない。
- レビューの指摘で直したもの: 別のリポジトリの相手の呼び名に `sessionLabel()` を使っていたので、表示名の無いセッションでは題名（相手のリポジトリの人の入力の 1 行目）が送り元へ流れた → 表示名か `#<worktree 名>` だけ。名前の一致に worktree 名も使っていたので、送り元の側の同じ名前のセッションがアーカイブ済みだと、`main` のような名前だけで別のリポジトリへ届いた → 別のリポジトリの相手は id と表示名だけで当て、送り元のリポジトリに同じ名前が居れば送らない。組を外しても、相手の預かりにもう並んでいた分は届いた → 外したときに取り消す。組を丸ごと置き換える口だったので、古い写しのタブが外した組を戻せた・記録の窓から出た古い組が 1 つあると何も変えられなかった → 1 つずつ足す・外す口にし、いまある組は検査し直さない。選べるリポジトリを `fillRepo` 前の一覧から作っていた・読めないと設定の応答ごと落ちた → 送信の判定と同じ一覧から作り、読めなければ空。送信の応答と断りの文に、一覧で伏せた読み直す量が出ていた → 出さない。
- 見送ったもの: `sai_sessions` が持ち場の集計を 2 回回す（速さだけの指摘）。
- 画面を撮って分かったこと: メニューのボタンは幅 100% の決まりがあり、行の中に置いた「やめる」が幅を取り切って、組の文字が 1 文字幅に潰れた。行の中のボタンは幅を戻した。メニューが画面より長くなるので、高さに上限を付けて中でスクロールするようにした。

### 相手で回っているターンは止めない

- CLI を殺すと相手の会話が途中で切れる。

## tailnet から MCP で呼ぶ口

### `sai_sessions` に待ちと最後の記録の時刻を載せた（#323）

- Manager が本文を読まずに急ぐものを選ぶため。

### `isCrossOrigin()` を使わない

- `Origin` は MCP の仕様（DNS rebinding）として必ず検査する。`isCrossOrigin()` は CLI が Origin を付けないので歯止めにならず、代わりが capability。

### 回数を `McpSendLimiter` で縛る

- tailnet から呼ぶ側は SAI が起動したターンではないので、1 ターンの回数では縛れない。呼んだ人ごとに 10 分 5 回にした。

### 素通しのセッションに送らない

- 呼び出し元の LLM が許可を聞かないエージェントを動かせてしまう。

### 案を置く `sai_suggest` を別の範囲 `draft` にした（#565）

- 前は Manager の提案をフィードで `@` から宛先を選んで貼っていた。宛先を選び直す手間と貼り間違いを減らすため、宛先の入力欄に「案」として置けるようにした。
- `send` に入れると capability が要り、ループバックの Manager（`.mcp.json` の `sai-read`）から使えない。かといって `read` に入れると「読むだけ」の前提が崩れるので、3 つ目の範囲にした。置くだけでターンを起こさないので、ループバックと tailnet のユーザーには既定で与える。
- 自動の許可（`.claude/settings.json`）には入れない。人の入力欄に書くものなので、置くたびに人が承認する。スキルも「人が『置いて』と言ったときだけ」にした。
- 別のリポジトリ・素通しのセッションにも置ける。`sai_send` が素通しに送らないのは、呼び出し元の LLM が許可を聞かないエージェントを動かせてしまうためで、案は人が入れて送るまで何も起きない。
- 24 時間と「人の入力が後に来たら消す」は、古い文脈の案が入力欄に残り続けないため。消すのは読むときの判定で、ファイルは次に置くときに掃除する（3 秒ごとの応答で書き込まない）。
- 「人の入力が来たか」は、はじめ `last_user_ts` と置いた時刻を比べていた。レビュー（#586）で、ターン完了の行も `last_user_ts` を進める（その行の `user_text` はそのターンを始めた入力）ため、処理中に置いた案がそのターンの終わりで消える、と指摘された。Codex は入力の行を書かないので、処理中の Codex に置いた案は必ず消えていた。次は置いたときの `last_user_text` と `turns` と比べる形にしたが、2 回目のレビューで `turns` は窓（一覧 7 日・詳細 90 日）で数えが変わるので例外が効かないこと、1 行目が同じ入力（「続けて」など）を見逃すことを指摘された。いまは置いた時刻より後のそのセッションの行を数える（入力の行が 1 本でも来たら、ターン完了の行は 1 本・処理中に置いたときは 2 本で「来た」）。3 回目のレビューで、Claude はバックグラウンドのタスクが終わると入力の行無しに自分でターンを回すことがあり、そこで消えると指摘された（実機では未確認）。一度は Claude / Grok でターン完了の行を数えないようにしたが、4 回目のレビューでフックが `Stop` だけの構成（README で案内している）では入力が分からず 24 時間残ると指摘された。`record.py` は自分で起きたターンの `Stop` に `user_text` を載せない（`last_user_text()`）ので、エージェントで分けずに「`user_text` のあるターン完了の行だけ数える」にした。
