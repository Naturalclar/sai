# 記録と集計の経緯

なぜ今の形になったか（前はどうだったか・実測・レビューの指摘）。仕組みは [internals/aggregate.md](../internals/aggregate.md)。新しい経緯はこのファイルの該当する節に足す。

## 同じ cwd の Codex の完了行が別スレッドに付いていた（#735）

- Codex 0.160 の notify には `session_id` は無いが `thread-id` がある。それを読まず cwd の一番新しい rollout を選んでいたため、同じ worktree で 2 本のターンが同時に走ると、あとから rollout を更新した別スレッドへ完了行が付いた。
- `thread-id` の rollout を直接引き、そこから `session_meta.session_id`（レビューなどの子スレッドなら親）を読む。古い notify と、未知の `thread-id` だけは従来の cwd による解決へ戻す。

## Codex のレビューの行が別のセッションになっていた（#403）

- レビューの子スレッドの rollout と親の rollout のどちらが cwd で当たるかは mtime の差（実測 5ms）で決まる。`session_meta.session_id` を先に見ていなかったころは、レビューの行が別のセッションとして現れることがあった。
- `review/start` の英語の指示文を置き換えないと、セッションのタイトルが英語の指示文になる。

## 1 つだけ出す値を「値のある一番新しい行」にした（#283）

- 前は `orderedUnique(...)` の最後（`sources[sources.length - 1]` の形）を使っていた。これは「一番新しい行の値」ではなく「最後に初めて出てきた値」。
- リポジトリ A の試作フックが書いた `session_source` の無い行（#54 の残り、21 本）が 1 セッションに混ざっただけで `sources = ['payload', '']` → `''` になり、そのあと `payload` の行が 360 本続いても「IDの出どころが不明」で返信を弾き続けた（90 日の窓から落ちるまで直らない）。
- ブランチも `A` → `B` → `A` と戻ったセッションで `B` のまま見出しに出ていた（43 セッション中 5）。

## 絞り込みを `repo` から `project` にした（#163 / #182）

- `repo` で絞ると worktree ごとに 1 セッションずつ並んで絞り込みにならなかった（#163）。
- `rowProject()` が `repo` に落ちていたころは、worktree 名が絞り込みの候補に混ざって汚れた（#182）。
- `repo` の値そのものは変えない: エンティティ ID が変わると `session-meta.json` のキー・アイコン・アーカイブ・URL がずれる。

## 仮バブルが 2 つ並んでいた（#375）

- 入力の行だけを見て仮バブルを消していたころは、Codex と OpenCode（入力の行を書かず `user_text` がターン完了の行に載る）で本物の自分バブルと仮バブルに同じ文が 2 つ並んだ。

## 「処理中」をファイルにも持つ理由（#100 / #440）

- サーバの再起動で「処理中」を忘れて、同じセッションに返信が二重に走った（#100）ので `replying.json` に書くようにした。
- MCP サーバは前は 1 回 SAI に届かないだけで拒否に落ち、立て直すたびに答え待ちの許可が拒否になっていた（#440）。
