# Codex の端末とapp-serverの経緯

なぜ今の形になったか（前はどうだったか・実測・レビューの指摘）。仕組みは [internals/codex.md](../internals/codex.md)。新しい経緯はこのファイルの該当する節に足す。

## ダイアログの検出

- アーカイブ済みを除く前の一覧を渡すのは #332 の原因 3。ターンの途中の質問では新しい行が届かず自動では戻らないので、除くと「アーカイブしたまま止まった」が見えなかった

## ダイアログの中身を読む（#425）

- 引用の枠（`  │ …` / `  └ …`）で止めるのは、実機の `gh pr create` の許可で見出しが `│` になったため
- 深い字下げの行を辿るようにしたのは #595。前は「ちょうど 2 文字下げ」の行だけを辿っていたので、折り返した 2 番の選択肢（`don't ask again for commands that start with <コマンド全文>`。続きは 5 文字下げ）で止まり、塊が `3. No…` の 1 行だけになった。実機（`gh pr create --body …`、幅 272 文字のペインで 3 行に折り返し）では見出し・コマンドが空、ボタンは「No」だけ、印が読めないのでそれも押せず、要対応に 30 分以上残った。コマンドが長いと必ず起きる
- 辿ったあとに頭を切り直す（`headStart()`）のは、`└` の下のツールの出力（4〜5 文字下げ）がダイアログのすぐ上に来ることがあり、そのまま入れると出力の 1 行が見出しになるため

## ダイアログに画面から答える（#450）

- 構造化された質問や選択肢を受け取る口は Codex の TUI には無い
- 実機 0.154.0 で測った: 数字キーは効かず、矢印＋ `Enter` と近道キー `y` が効いた。近道キーはラベルの読み方に依るので使わず、矢印に揃えた
- 「今後も確認しない」（`don't ask again`）をボタンにしないのは、効く範囲が読み切れないため。#421 の OpenCode の `always` と同じ
- 半分しか読めなかったものを答えられない側にしたのは #595。前は `answerable: dialog !== null` で、選択肢が 1 つでも読めれば答えられる扱いだった。上の読み違いでは「No」のボタンだけが出て、押すと `409`（印が読めない）になった。塊は下から辿るので欠けるのはいつも上で、番号が 1 から続くかと印の数で見分けられる

## 行の pid が死んでいるときの補欠（#332 の案 2）

- notify を README のラッパー経由にしていると、#335 より前の行はすぐ終わるシェルの pid を持っていて `terminalOf()` が null を返し、ペインでは Codex が動いているのに許可待ちの検出にも端末への打ち込みにも回らなかった（実測で、案 1 のあとも 3 つのペインが該当）
- 見つからなかったことも覚えるのは、3 秒のポーリングのたびに `lsof` を起こさないため

## 行の pid が生きていてもペインの中かを見る（#562）

- codex 0.153 の TUI は共有の `codex app-server --listen unix://` の客のことがあり、notify を鳴らすのは app-server なので行の `pid` は tmux の外（ppid 1）、`pane` は app-server を起こしたペインの `TMUX_PANE` になる（実測）
- 実測で 1 本の app-server がスレッド 4 本・tmux の客の TUI 3 つを抱え、kanban と dotfiles の会話の行も sai の TUI のペインを指していた。生きているだけで端末とみなすと別の会話の TUI を端末と取り違えうる
- 「そのペインの TUI がその app-server の客か」で当てる案は捨てた。どのスレッドを映しているかを言わないので、別の会話に打ち込む（#566 のレビュー）

## 客の TUI を起動時の会話に結ぶ（#568）

- app-server に客ごとのスレッドを聞く口は無い（159 メソッドを調べた。`thread/loaded/list` はサーバ全体で、`/new` や TUI の終了後も載ったまま）。TUI もいまのスレッド ID をどこにも書かない。そのため材料を重ね、1 つでも合わなければ当てない形にした
- 前の「起動後に同じ cwd の rollout が書かれていれば当てない」（#557）は、誰も開いていない別の会話でも空に倒れていた（実例: dev-codex の TUI と同じ worktree の別の会話が、別のプロセスから書かれていた）

## ペインの側から探す（#417 / #429 / #434 / #435）

- realpath に揃える（#434）: `lsof` が返すのはリンクを解いた実パス（実測で macOS の `/tmp/…` は `/private/tmp/…`）なのに、`root` は `CODEX_HOME` / `homedir()` を書いたとおりに繋いだものなので、`CODEX_HOME` を `/tmp` の下に置く・`~/.codex` を別のボリュームへリンクすると前方一致が 1 本も当たらず、例外も出ないまま検出が黙って何も返さなかった
- cwd から引かない（#429）: 前は `record.py` の `resolve_codex_session()` と同じ「その cwd の一番新しい rollout」を使っていた。あちらは自分が書いた行を処理する向き、こちらはペイン → セッションを当てる向きで、同じ worktree に会話が 2 本あると崩れる。端末で 1 本開いたまま SAI から新しいセッションを起こす（#401）と、新しい方の rollout が一番新しくなってペインの導出セッションが別の会話に化け、その会話の TUI に返信が打ち込まれた（1 つの cwd で 2 ペイン開いている場合も同じ。`inspectPrompt()` はどちらも本物の codex なので弾けない）
- 引けなければ空、は #417 以前と同じ「端末として見つからない」に落ちるだけ
- 実測（手元の 9 ペイン）では 7 つが rollout を開いたままで、引けなかった 2 つは 5 日放置した TUI（fd を閉じている）と一度きりの `codex "…"`（そもそも対話セッションではない）だった
- lock から引く手は codex 0.153.2 でしか当たらない（実測で 0.154.0 の TUI は lock を開かず、そのスレッドの lock は ChatGPT アプリの `codex app-server --listen`（tmux の外）が握っていた）。ペインの側から探すのはこのため
- 行のあるセッションを `paneOnlyTargets()` に足さないのは、id の組み立てが違うと同じ待ちが 2 回出るため
- tmux が落ちたときに前の結果を捨てないのは、「1 つも開いていない」と決めつけないため
- 失敗も覚える（#435）: 前は catch が `cache.at` を進めていなかったので、tmux の無いマシンでは cache が一度も埋まらず、3 秒のポーリングで応答を組むたびに `tmux list-panes` を起こし直していた
- 実測で 8 ペイン 578ms、2 回目は 0ms。rollout の 1 行目（`session_meta`）は実測 18.5KB あるので、頭は 64KB 読む

## 走査の締切（#495 / #496）

- Mac が重いとき（一言を作る Ollama など）に `ps` 1 本が 2 秒になり、一覧の初回が 38 秒になっていた（#495）
- 締切を付けても、画面の道は**ほぼ毎回 0.7 秒の締切に当たっていた**（#592 の実測。一覧 1 回で子を 14〜22 本、詳細で 4〜6 本起こし、`tmux` + `ps` + `capture-pane` を対象ごとに毎回。`claude agents` の TTL もポーリングと同じ 3 秒で、詳細は毎回それを待ち切っていた）。走査を 5 秒覚え、`ps` を 1 回の走査で 1 本にし、前回の結果があれば待たずに返すようにした。数えたのは `scripts/count-spawns.mjs`
- #599 のあとも、起こす子の半分（272 本中 137 本）が対象ごとの `tmux display-message` + `capture-pane` だったので、走査 1 回で全員ぶんを 2 本にまとめた（`sharedTmux()`）
- 相手ごとに覚えるのは #599 のレビュー。走査全体で 1 つの結果を持つと、絞り込んだ口（MCP の `project` つき）の走査が一覧の結果を置き換え、待たずに返すようにした分、別のリポジトリのダイアログが 1 回ぶん消えて見えた
- 返信の振り分けとレビューの断りを待ち切るのは #496 のレビュー。前回の結果が空の再起動直後に締切で抜けると「端末で開いていない」と読み、開いている TUI の会話をレビューが奪い、返信が端末に打ち込まれず別プロセスや queue に回る

## ターンを止める（#384 / #392 / #488）

- 別の接続のスレッドは app-server が `thread not found` で断るので、端末で人が回している Codex には手が出ない（画面から人のターンを殺さない）
- 預かりを先に止めるのは、実測で `turn/interrupt` のあと `turn/completed` が届き、それが `onTurnEnd` → `drain()` に繋がっていて、止めた直後に次の預かりが走ってしまうため
- 実測（codex 0.154.0）では `{}` が 11ms で返り、`thread/status/changed: idle` と `turn/completed`（`status: "interrupted"`）が続く
- そのターンが起こしたシェルのコマンドは残る（`sleep 120` が app-server の子として生き残った）
- OpenCode（#392）は 1.18.30 で実測: 0.2 秒ほどで返り、`/session/status` から消え、最後のメッセージに `MessageAbortedError`、プラグインの `session.idle` で本文の空の行が 1 本書かれる。`abort` は回っていないセッションにも知らないセッションにも `true` を返す
- serve が居なければ止まった扱いにするのは #488 のレビュー。false を返すと「起動した直後なので止められない」の 409 になり、効かない「止める」と「処理中」が残り続ける
- Claude の `-p` に SIGINT を送る案は「閉じないまま残るターン」を増やすだけなので、別に測ってから
- #597 のレビュー: 遡るほうは深い字下げを辿るようにしたが、**塊の最後の行**の検査はそのままで、最後の選択肢（`No, and tell Codex what to do` / `differently (esc)`）が折り返すとダイアログごと読めなかった。終わりの行が無いときは続きがラベルから落ちていた。また `answerable` は印の読め方で変わるのに `approvalMapKey()` が `approval_id` しか見ず、描き直しの途中を 1 回読むと画面が「読めませんでした」のまま残りえたので、鍵に混ぜた。
