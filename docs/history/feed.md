# feed の経緯

なぜ今の形になったか（前はどうだったか・実測・レビューの指摘）。仕組みは [internals/feed.md](../internals/feed.md)。新しい経緯はこのファイルの該当する節に足す。

## feed/record.py

### 締切に間に合わなくても `Stop` の行は書く（#613 の案 2）

- #619（transcript を末尾から読む）のあとも、4 セッションが同時に終わる場面で `Stop` の行が落ちた（10/1 17:32 に 2 件。`sai-record` が 16.7 秒・16.2 秒）。速くするだけでは、混んだときに落ち続ける
- 行が無いと画面は「まだ回っている／止まった」の区別が付かないので、本文が空でも行は書く。本文の無いターン完了の見せ方は #614
- 15 秒は延ばしていない（フックが長く掴むとエージェント本体の終わりが遅れる）。代わりに 12 秒で読むのを切り上げる。**10〜15 秒かかっていたターンは、前は本文つきで書けていたのが、12 秒を過ぎた分は空になる**（落ちるよりはよい、という判断）
- 混ませた測定（本物の transcript の写し 71〜96MB を 4 本同時に `Stop`。空回りを background QoS で 450 本、load average 330〜345）: 前は 8 回中 1 回が行なし・2 回が SIGALRM で非 0 終了、後は 8 回とも行あり・exit 0。150 本・240 本では前後とも 12 回中 12 回書けた。CPU の空回りでは本物の混み方（17:32）をそのまま再現できず、**壁時計のほとんどは `python3` の起動待ち**だった
- 非 0 終了はこの測定で見つかった別の不具合（終了間際にアラームが届く）。「必ず exit 0」が破れていたので一緒に直した
- git の予算と `toplevel_name()` も同じ測定から。極端に混むと git の 4 回の呼び出し（各 3 秒で時間切れ）が 15 秒を使い切り、読み取りに着く前に保険に掛かっていた
- 跡を既定で残すか（issue の「決めること 2」）は入れていない

### 「直前の行」を `ts` で選ぶようにした（#439）

- 新しい日から積んで「最後の要素」を採っていたころは、日をまたいだセッションで前日の最後の行が「直前」になり、今日の行が全部飛ばされていた（実データで、重なって書かれた `permission_prompt` の 29 件すべてが「前日のファイルにも同じセッションの行がある」回だった）。
- 2 日ぶん見るのは今までどおりで、変えたのはその中のどれを採るか。

### 知らない `event` を `other` に落とす（#235）

- 以前は既定が `turn` だったため、`SubagentStop` / `session-configured` のような行が「一番新しいターン完了」を奪って一覧の「最後の発言」が空になり、`last_turn_ts` がずれて一言が消え、`turns` も水増しされていた。

### Claude の `text` をそのターンの返答に限る（#467）

- 前は transcript の末尾から最初に見つかった assistant の本文を返していて、ターンの境目（`_is_prompt_row()`）で止まらなかった。
- `Stop` フックはそのターンの最後の行が transcript に書かれる前に走るので（実データで行の `ts` の 0.1〜0.89 秒あと、中央値 +0.50 秒）、遡った先が前のターンの返答になり、人が頼んだことと無関係な「前回と同じ返事」が記録されていた（Claude の Stop 行 1397 本中 39 本、うち 22 本が前のターンの返答そのもの。セッションによっては 26 本中 17 本）。
- 古い閉じた行を先に返さない理由: 実データの `stop_sequence` は 30 件すべて Claude Code の合成通知「You've reached your … limit」だった。
- `ASSISTANT_IDLE_S` の 1.2 秒は、実測の遅れの最大 0.89 秒に余裕を持たせた値。閉じた行が来ないターンは実データで 6.9%。
- 実データ 1547 ターンで競走を再現すると、いまのターンに無い本文を返したのは 672 件（43.4%）→ 0 件。

### transcript を末尾から読む（#613）

- `Stop` の行が黙って落ちていた: 2 つのセッションで `sai-record` が 16〜17 秒かかり、15 秒の自殺タイマーに掛かって行を書かずに exit 0 した。画面には「依頼を受けたまま」に見えた。
- 測った（88MB・19,820 行の本物の transcript の写し、`AGENT_FEED_DIR` は一時ディレクトリ）: 全行の `json.loads` が 1 回 0.65 秒（負荷平均 10）で、`Stop` の 1 回の実行がそれを 4〜5 回（本文・入力・思考・モデル、待っている間に増えればもう 1 回）繰り返して 4.3 秒。ファイルを読むだけなら 13ms、`python3` の起動は 42ms。**CPU を取り合うと同じ 1 回が 14.8 秒になり、フックは 17.3 秒で行を書かずに終わった**（再現）。時間は「行数 × 読む回数 × 混み具合」で決まっていた。
- 直したあとは同じファイルで 4 つの読みが合わせて 1ms、フック全体は 2.2 秒（うち 1.2 秒は #467 の「閉じた行を待つ」ぶんで、写しが増えないため上限まで待っている。本物では閉じた行が見えた時点で終わる）。
- 本物の transcript 127 本で、直す前と後の 4 つの値が全部同じことを確かめた。15 秒は延ばしていない。本文の上限・前のターンに遡らない・古い閉じた行を先に返さない（#467）もそのまま。

### 自動の要約の行を人の入力にしない（#626）

- Claude がターンの途中で自動の要約（compact）をすると、そのターンの `Stop` の行の `user_text` が要約の文（`This session is being continued …`。1 行 9,000〜18,700 字）になっていた。transcript の要約の行は `type: user` で、`last_user_text()` と `_is_prompt_row()` は `isMeta` と `isSidechain` しか飛ばしていなかった。処理中の手順を読む側（`claudeProgress()`）は `isCompactSummary` を飛ばしていて、**同じ「人の入力か」の判定が 2 か所にあり、片方だけ直っていた**。
- 実測（2026-10-02。記録の写しと transcript を読んだだけ）: `user_text` が要約の行は 9/9〜10/2 で 48 行、どれも `Stop`。その 48 行それぞれについて、transcript を行の時刻で切って直した `last_user_text()` に読ませると、48 行とも人の入力になり、48 行とも入力した瞬間の行（`UserPromptSubmit`）の `user_text` と同じ文だった。
- 困っていたこと: セッション同士のメッセージの返答が送り元に戻らない（見出しの id が消える）、画面に 1 万字超の要約が自分の発言として並ぶ、題名が要約になる、「長い入力」の集計が狂う（#609）。
- 読む側（もう書かれた行）: 記録は書き換えず、`shared/compactSummary.ts` の `isCompactSummaryText()` で飛ばす。同じ写しで、自分のバブルが要約になっている発言は 48 → 0、送ったメッセージ 33 通のうち返答が引けたのは 20 → 22（`dc9068d1` を含む）。
- 記録の側は印だけ、読む側は決まり文句で見る（もう書かれた行には印が残っていない）。人が同じ文で書き出した入力は読む側で要約扱いになるが、Claude Code が要約の頭に置く 1 文そのままなので割り切った。

### 本文の上限を 20000 字にして `clipped` を載せる（#358）

### 送る前に状態を空にする（#392）

- `send()` は record.py の終了を待つので、送ったあとで空にしていたころは、その間に届いた次の idle が同じ行（自分の入力つき）をもう 1 本書いていた。
