# 返信の経緯

なぜ今の形になったか（前はどうだったか・実測・レビューの指摘）。仕組みは [internals/reply.md](../internals/reply.md)。新しい経緯はこのファイルの該当する節に足す。

## 端末（tmux）

- 端末に打ち込んだ・queue に渡した返信で、ターンが始まらなかったものは、前は 30 分の TTL で黙って消えた。いまは `TERMINAL_DELIVERY_WAIT_MS`（2 分）で `failed` にして画面に出す。

## 子プロセスの環境（childEnv。#234）

- `TMUX_PANE` を渡していた頃は、子がサーバの環境をそのまま継ぐので、`pnpm start` を打ったペインが `record.py` 経由で全セッションの `pane` として記録された（手元では 6 つの worktree のセッションが 1 つのペインに付いていた）。
- その結果 `SessionSummary.terminal` が偽陽性になって「端末で開いているから処理中でも送れる」と誤判定し、二重起動の歯止め（#100 / #170）まで外れていた。
- `isDescendant()` はこれを弾けない（`-p` の子はサーバの子孫で、サーバはそのペインの子孫なので条件を満たす）ので、環境で落とすことにした。

## 終わらない CLI（#375）

- 実測で `opencode run -s` が該当した: 本文つきの行を書いた 37 秒後から 15 分以上 CPU 0.1% で生き残り（9/10 は 1 時間 23 分で手 kill）、Node の `spawn` から起こしたときだけ再現する（`detached` の有無・stdio の渡し方 4 通りで同じ。シェルからは 5/5 とも正常終了するので、SAI の起こし方ではなく OpenCode 側の挙動）。
- 子の `exit` だけを見ていると「処理中」が永久に消えず、以後の返信が全部預かりに回り、いつかプロセスが死んだときに `drain()` でまとめて走る（= 同じ指示が 2 回）。そのため行が届いたら終わりにする。

## Claude の使用量（#387 / #411）

- 子の stdout を pipe にすると、サーバを立て直したときに引き取った子が書き込みで死ぬ。そのためログの fd に直接書かせたまま、終わったあとに reply.log から読む形にした。
- タグの文字に費用を出さないのは、定額プランでは請求額ではないため（`title` にだけ出す）。
- 行と使用量の向き: `Stop` フックはターンが終わった時点で走り CLI はそのあと終了するので、使用量が必ず後にできる（実測 0.6〜1.5 秒）。後ろの行は見ないので、次のターンのぶんが前のバブルに付くことはない。
- 窓（`USAGE_MATCH_MS` = 2 分）を広く取らないのは、行を書かずに終わったターンのぶんを 1 つ前のバブルに付けないため。
- #602: バブルの印の「費用」が、そのターンぶんではなくセッションの積み上げだった。CLI の `total_cost_usd` は `--resume` で続けたセッションの合計を返す（10/2 の実測で 970 行のうち、前の行より下がるのは 82 回だけ）。単純に足すと 85,857 ドル、前の行との差で数えると 3,257 ドルで、26 倍ずれる。ファイルは CLI の値のまま（書き換えない）にして、行に載せるときに差に直した。
- #602 のレビューで分かったこと: **積み上げになったのは 9/19 ごろから**で、それより前の 166 行は 1 ターンぶんだった（日ごとの「前の行以上」が 9/16〜9/18 は半分ほど、9/19 から 37/41・29/29・103/105…）。issue の「822 行のうち 740 行が前の行以上」は全期間をならした数字だった。なぜ変わったかは分かっていない（SAI のその日のコミットには無い）。行からは区別が付かないので時刻の定数で切った。行に印を足す案は、原因が分からないまま「積み上げ」と書くことになるのでやめ、古い行の費用を出さない案は、正しい数字を捨てるのでやめた。使用量の画面は最大 30 日なので、古い行は 10/19 にどの期間からも外れる。**CLI がまた 1 ターンぶんに戻ると、差で数えた費用が小さく出て気づけない**（別 issue）。費用が 0 の行で「前の行」を忘れ、次の行に積み上げが丸ごと乗る不具合も同じレビューで直した（40.469 → 0 → 45.608）。
- #602 の画面: 「読み直し大」を返信の数でなく CLI の中で回ったターン数（`num_turns`）で割るのは、1 回の返信の中でモデルを何度も呼ぶため（返信の数で割ると、どのセッションもコンテキストの上限より大きく出る）。入口を自分のメニューにも置いたのは、帯の使用量（`UsageChip`）が取れないマシンでは出ないため。狭い画面で名前の列を `max-width: 0` のままにしたら、列が潰れて隣の数字に重なった（撮って気づいた）ので、決まった幅にして表ごと横に送る。

## Codex

### queue と writer lock（#329）

- Codex が終わっても lock のファイルは残る。前はそれを読んで、閉じたセッションへの返信を誰も受け取らない queue に渡していた。そこで「開いているプロセスがいるか」（`lsof -t`）で数えるようにした。

### queue に渡した返信が届かない（#474）

- VS Code 拡張・ChatGPT アプリの裏で動く共有の `codex app-server --listen`（tmux の外）がスレッドの writer lock を握ったまま、どの画面もそのスレッドを開いていないと、`codex queue` は exit 0 のまま本文はターンにならずに消える（実データで queue 36 件中 7 件）。
- mtime は「何か書かれた」でしかないので、本文が rollout に現れたかで見ることにした。
- 別の app-server が握っている間は、SAI の app-server からの `thread/resume` も `thread … already has an active writer` で断られる（使い捨てのスレッドで実測）。届けに行く経路は無く、届かなかったことを早く・消えずに出すのが直し方になった。
- queue は届いたときの遅れが 0〜10 秒なので 30 秒で確かめる。失敗を 30 分見せるのは、前は端末の失敗と同じ 2 分で消していて、送って 2〜4 分の間に画面を見ていないと失敗は一度も目に入らず「送ったのに静かに終わった」になっていたため。
- 宛先がターンの途中なら判定を保留する理由: 回っているターンが終わってから queue の本文が流れるなら、30 秒で「届いていない」と決めるのは誤りで、言われたとおり送り直すと同じ指示が 2 回走る。実データには「ターン中に queue で送った」回が 1 件も無く、待たされるかは確かめていないので、保留する側に倒した。
- 実データの queue 36 件で「送って 30 秒後に見た状態」を再現すると、行が残った 20 件はすべて届いた・一度も現れなかった 7 件はすべて届いていない、で誤りは 0。

### エラーで終わったターン（#475）

- codex 0.154.0 で実測: 使い捨ての `CODEX_HOME` で、無いモデルを指定したターンは `turn/completed` が `status: "failed"`・rollout の `task_complete` に `error` が付き、notify は呼ばれなかった。共有の `codex app-server --listen` が回したターンでも、成功すれば notify は鳴ることも同じ手順で確かめた。
- 実データでは queue に渡して届いた返信の 2 件が `You've hit your usage limit.` で終わり、画面からは「送ったのに返事が来ない」だけに見えていた（9 月の rollout で、エラーで終わったターンは 2 件とも行が無く、成功したターンは 82 件すべて行があった）。

### 配送済みの返信を 30 分で消さない（#559）

`TerminalReplies.settle()` が配送済みかに関わらず 30 分で「処理中」を消していたので、長いターンは終わっていないのに仮バブルが黙って消えた。配送済みは消さないようにしたが、レビューで 2 つ直した: **行が届かないまま終わるターン**（Esc で止めた Claude は Stop フックが鳴らない。ペインを閉じた）があるので、上限が無いとその返信が永久に「処理中」でそのセッションへの返信が 409 で断られ続ける → 6 時間の上限。**材料が無いときに「届いた」と答えていた**（一覧の窓に無い・別のマシン・Claude と Codex 以外）のが、上限が延びるようになったことで害になる → null（決めない）に。あわせて、行で終わった返信の配送を rollout を読んで確かめていた無駄を、先に行だけで片付けることで無くした。

### 許可（#421 / #422）

- `GET /permission` に `directory` を渡さないと保留が 1 件あっても `[]` が返ることは実機で確認した。

## 始める場所を兄弟 worktree に広げる（#319）

- 2026-09-11 の手元: `ghq list` 47 リポジトリの worktree 77 のうち、90 日の記録にあるのは 15（リポジトリでは 6）。記録のあるリポジトリの記録の無い兄弟 worktree が 11。記録にある `cwd` 26 件には `/`・`/tmp`・scratchpad が混ざっていて、そこでも始められていた。
- 決めたこと（2026-09-30）: 広げるのは**記録のあるリポジトリの worktree**（`git worktree list`）まで。**ghq の下の全リポジトリ（案 B）はやらない**——同一オリジンの守りが破られたときに走りうる場所が数倍に広がる。一度も記録の無いリポジトリは、端末で 1 ターン回せば候補に出る。**画面から worktree を作る口（案 C。#389 の `claude -w` も）もやらない**——SAI から始めた 59 回を数え直すと、記録の無い worktree はエージェントが PR の作業用に自分で切ったものだった。git に書く口は増やさない。
- 実測（2026-10-01）: bare clone の中の worktree から `git worktree list --porcelain` を呼ぶと、先頭に bare 本体（`bare`）、消えたもの（`prunable gitdir file points to non-existent location`）、`/private/tmp` の下の worktree まで兄弟が全部出た。`locked` は中身があるので候補に残す。手元の記録で候補を作ると、git の外の 22 か所（`/`・`/tmp`・scratchpad など）が落ち、兄弟 worktree が 16 足された（最初の 1 回は 26 か所の `git worktree list` で約 4 秒。30 秒は覚える）。
- 記録の無い worktree で record.py が書く行: `repo` はその worktree のディレクトリ名（`sai-issue-448` / `dev-lyrica`）、`project` は記録のある worktree と同じ（`Naturalclar/sai` / `AnotherBall/persona-server`）。そのためエンティティ ID の `repo` を `from` から借りず、その worktree の名前で組み立てる。

## claude --bg（#462）

実測（2.1.276〜278）で分かった 4 つがこの形を決めている。

- デーモンは起動した側の環境を継がない: `AGENT_FEED_DIR` を環境で渡しても record.py に届かず本物の置き場に書かれた。
- `--permission-prompt-tool` は使われない: MCP サーバは起動するが `approve` は呼ばれず TUI のダイアログで止まり、`claude agents` では `status: waiting`。
- `--session-id` は効かない。
- 生きている bg のセッションには `-p --resume` が断られ、`--bg --resume` は別のセッションに写す（止めたあとにフラグ無しで打つと同じ ID で起きるが、起動時の設定のまま）。

そのほか:

- 2026-09-24 に実測: `claude stop` は attach している端末を `Session … has exited.` でその場で閉じ、打ちかけも消える。これが「attach していれば止めない」理由。
- `ps` で素朴に `attach` を含む行を探すと、SAI 自身の `claude -p` の `--mcp-config` の中の `attachments` に当たった（実測）。そのため `claude` `attach` `<ID>` が続けて並ぶ行だけを数える。
- 2.1.278 の `claude agents` はバックグラウンドの行に `state` しか持たず（`status` も `pid` も無い）、2.1.276 は `status` = `busy` / `idle` / `waiting` だった。
- 返信のたびに `claude agents` を起こすと、端末に打ち込む経路より手前で 0.15〜0.20 秒増える。そのため覚えているものを先に見る。

## 預かり・steer

- #170: 長いターンの間フィードから何も送れないのを避けるため、端末に打ち込む経路は処理中でも通すことにした。
- #305: 別プロセスの経路で処理中に送った分を 409 で断る代わりに預かるようにした。前の返信が失敗していたら回さないのは、失敗したターンの続きを黙って積み上げないため。
- #404: `turn/steer` の形（`{ threadId, expectedTurnId, input }`）と `expectedTurnId` が本当に守られること（別のターンなら `expected active turn id X but found Y`、終わっていれば `no active turn to steer`）は v0.154.0 で実測。既定を預かりにしたのは、動いているターンに足すのは「次のターンとして回す」と別の意味で、足した分は取り消せない（走っているターンの筋がその場で変わる）ため。

## Claude の `-p` を止める・足す（#386）

- 前は Claude の `-p` には止める口が無く `400` だった（`-p` に SIGINT を送る案は「閉じないまま残るターン」を増やすだけなので採らなかった）。「今のターンに足す」も Codex だけだった。
- 使用量のための `--output-format` を `json` から `stream-json` に変えた（入力の口を開けるには出力も stream-json にする必要があり、`-p` で stream-json を出すには `--verbose` が要る）。
- 実機（2.1.285）で確かめたこと: 止めたターンでは `Stop` フックが鳴らず、プロセスは exit 1 で終わる（だから止めた返信は失敗にしない）。足した指示では `UserPromptSubmit` が鳴り、`Stop` の行の `user_text` は元の指示のまま。許可・質問の配線はこの入力の形でも今までどおり動いた。途中で stdin を閉じてもターンは `result: success` まで走った（引き取った子を止められない理由）。
- reply.log は 1 ターンで 100KB ほどに育つ（`--verbose` の stream-json）。
- 長寿命の 1 セッション 1 プロセスにはしない（`claude` は 1 本 約 350 MB で worktree が 17 ある）。
- stdout を pipe にしないのは、立て直したあとに引き取った子が書き込みで死ぬため（#387 と同じ理由）。

## 要約してから送る（#579）

- 9/16〜9/30 に SAI が起こした Claude のターン 736 本で、トークンの **97.3% が会話の読み直し**（cache read）だった。worktree ごとのセッションを何週間も使い続け、自動の要約は文脈がほぼ満杯（直前の中央値 約 96.6 万）になるまで走らない。要約の直後は約 8.3 万、新しいセッションの最初は約 4.9 万
- 最初は「着手して」を新しいセッションで送る案だったが、**要約（同じセッションのまま）を既定にした**: 名前・アイコン・URL・未読・許可モードを引き継ぐ仕組みが要らない、同じ名前が 2 つ並ばない（#572）、学んだことが要約に残る、効き目はほぼ同じ
- 実機（2.1.285、haiku）で確かめたこと:
  - **`/compact` は stream-json の入力（#386）の `user` のメッセージとして通る**。`system/compact_boundary`（`trigger: "manual"`・`pre_tokens` / `post_tokens`）が出て、`session_id` は同じ、`result` は空・`num_turns: 0`・exit 0（29,555 → 3,448 トークン）。先に確かめたのは本文を引数で渡す形（`claude -p --resume <id> "/compact"`）だった
  - 添えた指示（「〈こと〉だけは残す」）のとおり、要約のあとでも残すよう頼んだことを答えた
  - **要約だけのターンは記録に行を書かない**（`UserPromptSubmit` も `Stop` も鳴らない）。「本文なし」のバブルは出ない
  - 要約のターンの `result.usage` は全部 0 で、量と費用は `modelUsage` と `total_cost_usd` にだけ載る
- **端末で開いているセッションでは既定にしない**（TUI に打ち込んだ `/compact` の最中に次の入力を受け付けるかを確かめていないため。別プロセスの経路だけで回す）
- 小さいセッション（15 万未満）は要約しない（要約しても得るものが無い）。量が分からないとき（詳細の `context_tokens` が 0）も出さない
- エージェントから頼むとき（`sai_send`）に同じ指定を付けるかは、まだ決めていない。Codex / OpenCode は対象外（要約の口があるかを別に確かめる）
- 送り方の select をそのまま行に置いていたら、携帯で送信ボタンが次の段に落ちた（#629）。タッチ端末では iOS の拡大を避けるために 16px にしていて、`max-width: 12em` が 192px になり、幅 390 の行の半分を取っていた。#579 のときは送り方が出ている状態を 390 幅で撮っていなかった（15 万トークン以上のセッションを作りものの feed で用意できなかった）。今回は詳細の応答の `context_tokens` をヘッドレスの側で差し替えて撮った
- #630 のあとも、**前の返信を処理中**のときは送信ボタンが落ちた（#631）。処理中だけ出る「今のターンに足す」（約 115px）と、長い方の文言「あとで送る」が重なるため。#630 の確認はどれも処理中でないセッションで撮っていた。状態ごとに出る部品が違う行は、状態の数だけ撮る

- 文字のファイルを元の拡張子で置くと `.html` / `.svg` という名前のファイルが置き場にできるので、全部 `.txt` にした（配る口の名前の検査を広げなくて済む）。元の名前は別のファイルに持ち、エージェントには行に添えて渡す（`build.log` のような名前は、エージェントにとっても何のファイルかの手掛かりになる）。
- 元の名前を返信のリクエストに載せる形にはしなかった（画面から来た文字列を本文に入れることになる）。預けたときにサーバが出せる形にして隣へ置き、返信のときはそれを読む。
- 選ぶボタンは写真と別にした（レビュー #667。1 つの口の `accept` を外すと、iPhone の写真が HEIC のまま来て中身の判定で弾かれるおそれがある。実機では未確認）。
- 自分のバブルに大きさは出していない（本文に載るのはパスと名前だけ。入力欄の並びには出る）。

## 許可モード

- #265: 見出しの `<select>` から入力欄のモデルの右へ移した。
- 「そのターン限り」は、フラグ付きで回したセッションをフラグ無しで再開すると元に戻ることを確かめた（`--model` と違う）。
- #272: `acceptEdits` で回っているターンの途中で素通しに変えると、そのターンは許可を聞き続けて「素通しにしたのに聞かれる」ように見えた。そのため起動したときのモードを `replying` に持つようにした。
- メタが素通しでも SAI が許可を自動で返さないのは、選んだ瞬間に起動済みのプロセスまで素通しになり、#253 の前提が広がるため。
- `bypassPermissions` でボタンを赤くするのは、そのセッションでは `isCrossOrigin()` が唯一の砦になるため（それ以外では「CLI が未許可のツールを拒否する」が二重目の歯止め）。
- 2.1.266 で実測: 許可は素通しになるが質問は素通しにならない（ツールの許可は `--permission-prompt-tool` を通らないが `AskUserQuestion` は通るので、質問のバブルはそのまま出る）。
- #271: 名前を英語にしたのは、Claude Code が端末の `Shift+Tab` で出す言い回し（`accept edits on` / `bypass permissions on` / `plan mode on`）に揃え、同じモードが端末と SAI で別の名前に見えないようにするため。UI 文言を日本語で書く方針の例外で、例外は名前だけ。

## モデル

- #394: `/api/model` の全件（手元で 93）ではなく `/config/providers` にしたのは、数の多さより、その人が実際に使えるものの方が当たるため。プロジェクト限定の provider が `directory` で現れ／消えることを実機で確かめた（サーバは homedir で動くので、渡さないと取りこぼす）。
- #282: 選択肢の名前を英語にしたのは隣の許可モード（#271）と揃えるため。言い回しは Claude Code のモデル選択から取った。未設定のボタンが許可モードと同じ `Default` になるのは意図的（どちらも CLI に任せる）。

## 別のマシン（#114）

- 複数マシンの JSONL を集めていると（#24 / #113）、ここでは再開できないセッションが一覧に混ざる（CLI も履歴もあちら側）。
- #288: 前はサーバが別の `SAI_HOST` を見ていて、README の手順どおり `AGENT_FEED_HOST` だけ設定すると自分のセッションが「別のマシン」になり返信の口が消えた。

## ループ（#634）

- はじめの案は 3 つあった: (a) 一定の間隔で同じ文を送る、(b) 終わりの条件まで回す、(c) エージェントが次に起きる時刻を自分で決める。**(c) を核にして (b) の「人が書く終わりの条件」を必須にした**。(c) だけだと続けるかも終わったかもエージェントが決めることになり、終わったループと詰まったループが外から見分けられない。(a) は「エージェントが時刻を言わなければ既定の間隔」という特別な場合として同じ仕組みに入れた。
- issue に残っていた「決めること」は、最初の実装では控えめな側に倒した:
  1. 終わりの判定は**エージェントが「終わり」と言ったら止める**（根拠を画面に出すだけ。SAI の側で確かめるコマンドは持たない）。
  2. 数字は 10 周・2 時間・既定 10 分・間隔 1〜60 分・同じ申し送り 3 周。使用量はセッション同士のメッセージと同じ歯止め（`usageRefusal()`）。
  3. **素通し（Bypass permissions）のセッションには組めない**。人が見ていない間に、何も聞かれずに回り続けるのを避ける。
  4. **Claude だけ**（「次」を言う口が `claude -p` に渡す MCP にしか無い）。
  5. **端末で開いているセッションには組めない**（打ち込む経路には MCP が無く、端末の `/loop` と二重に回るのを見分けられない）。
- 「毎周の頭に送る文」を人に別に書かせるのはやめ、目的と終わりの条件から SAI が組む（入力欄が 1 つ減り、ツールの呼び方を毎周同じ文で渡せる）。
- ツールを呼ばなかった周は「申し送りが同じ」に数えない（数えると、一定の間隔の見回りが 3 周で止まる）。
- `sai_loop_next` は周のターンにだけ見せる（`SAI_LOOP=1`）。いつも見せると、周でないターンで呼んで断られるだけのツールが毎回の一覧に載る。
- 周を起こすのを画面のポーリングだけにすると、画面を閉じている間は回らない。預かり（#305）はそれでよかったが、ループは人が見ていない間に回すものなので、サーバにタイマーを持たせた（見に行く相手がいる間だけ）。
- レビュー（#640）で 2 つ直した。(1) `tickLoop()` はループを 1 回読んだあと、セッションの一覧・`loopRefusal()`・使用量を await してから書いていたので、その間に人が「止める」「片付ける」を押すと古い状態で上書きし、止めたループが `running` に戻って次の周が起きた。書く前に置き場の値が読んだときのままかを見る（`moved()`）。(2) 素通しの断りが `SAI_CLAUDE_ARGS` の `--permission-mode=bypassPermissions`（1 語の形）を見ていなかった。
