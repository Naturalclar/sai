# 返信の経緯

なぜ今の形になったか（前はどうだったか・実測・レビューの指摘）。仕組みは [internals/reply.md](../internals/reply.md)。新しい経緯はこのファイルの該当する節に足す。

## 端末（tmux）

- 端末に打ち込んだ・queue に渡した返信で、ターンが始まらなかったものは、前は 30 分の TTL で黙って消えた。いまは `TERMINAL_DELIVERY_WAIT_MS`（2 分）で `failed` にして画面に出す。

## 子プロセスの環境（childEnv。#234）

- `TMUX_PANE` を渡していた頃は、子がサーバの環境をそのまま継ぐので、`pnpm start` を打ったペインが `record.py` 経由で全セッションの `pane` として記録された（手元では 6 つの worktree のセッションが 1 つのペインに付いていた）。
- その結果 `SessionSummary.terminal` が偽陽性になって「端末で開いているから処理中でも送れる」と誤判定し、二重起動の歯止め（#100 / #170）まで外れていた。
- `isDescendant()` はこれを弾けない（`-p` の子はサーバの子孫で、サーバはそのペインの子孫なので条件を満たす）ので、環境で落とすことにした。

## 終わらない CLI（#375）

- 実測で `opencode run -s` が該当した: 本文つきの行を書いた 37 秒後から 15 分以上 CPU 0.1% で生き残り（9/10 は 1 時間 23 分で手 kill）、Node の `spawn` から起こしたときだけ再現する（`detached` の有無・stdio の渡し方 4 通りで同じ。シェルからは 5/5 とも正常終了するので、SAI の起こし方ではなく OpenCode 側の挙動）。
- 子の `exit` だけを見ていると「処理中」が永久に消えず、以後の返信が全部預かりに回り、いつかプロセスが死んだときに `drain()` でまとめて走る（= 同じ指示が 2 回）。そのため行が届いたら終わりにする。

## Claude の使用量（#387 / #411）

- 子の stdout を pipe にすると、サーバを立て直したときに引き取った子が書き込みで死ぬ。そのためログの fd に直接書かせたまま、終わったあとに reply.log から読む形にした。
- タグの文字に費用を出さないのは、定額プランでは請求額ではないため（`title` にだけ出す）。
- 行と使用量の向き: `Stop` フックはターンが終わった時点で走り CLI はそのあと終了するので、使用量が必ず後にできる（実測 0.6〜1.5 秒）。後ろの行は見ないので、次のターンのぶんが前のバブルに付くことはない。
- 窓（`USAGE_MATCH_MS` = 2 分）を広く取らないのは、行を書かずに終わったターンのぶんを 1 つ前のバブルに付けないため。

## Codex

### queue と writer lock（#329）

- Codex が終わっても lock のファイルは残る。前はそれを読んで、閉じたセッションへの返信を誰も受け取らない queue に渡していた。そこで「開いているプロセスがいるか」（`lsof -t`）で数えるようにした。

### queue に渡した返信が届かない（#474）

- VS Code 拡張・ChatGPT アプリの裏で動く共有の `codex app-server --listen`（tmux の外）がスレッドの writer lock を握ったまま、どの画面もそのスレッドを開いていないと、`codex queue` は exit 0 のまま本文はターンにならずに消える（実データで queue 36 件中 7 件）。
- mtime は「何か書かれた」でしかないので、本文が rollout に現れたかで見ることにした。
- 別の app-server が握っている間は、SAI の app-server からの `thread/resume` も `thread … already has an active writer` で断られる（使い捨てのスレッドで実測）。届けに行く経路は無く、届かなかったことを早く・消えずに出すのが直し方になった。
- queue は届いたときの遅れが 0〜10 秒なので 30 秒で確かめる。失敗を 30 分見せるのは、前は端末の失敗と同じ 2 分で消していて、送って 2〜4 分の間に画面を見ていないと失敗は一度も目に入らず「送ったのに静かに終わった」になっていたため。
- 宛先がターンの途中なら判定を保留する理由: 回っているターンが終わってから queue の本文が流れるなら、30 秒で「届いていない」と決めるのは誤りで、言われたとおり送り直すと同じ指示が 2 回走る。実データには「ターン中に queue で送った」回が 1 件も無く、待たされるかは確かめていないので、保留する側に倒した。
- 実データの queue 36 件で「送って 30 秒後に見た状態」を再現すると、行が残った 20 件はすべて届いた・一度も現れなかった 7 件はすべて届いていない、で誤りは 0。

### エラーで終わったターン（#475）

- codex 0.154.0 で実測: 使い捨ての `CODEX_HOME` で、無いモデルを指定したターンは `turn/completed` が `status: "failed"`・rollout の `task_complete` に `error` が付き、notify は呼ばれなかった。共有の `codex app-server --listen` が回したターンでも、成功すれば notify は鳴ることも同じ手順で確かめた。
- 実データでは queue に渡して届いた返信の 2 件が `You've hit your usage limit.` で終わり、画面からは「送ったのに返事が来ない」だけに見えていた（9 月の rollout で、エラーで終わったターンは 2 件とも行が無く、成功したターンは 82 件すべて行があった）。

## OpenCode

### serve へ移した（#382）

- 実機（1.18.30）で確かめた前提が 3 つある: サーバでもプラグインは動く、セッションは ID だけで引けてそのセッションの cwd で走る、`OPENCODE_SERVER_PASSWORD` を渡せば鍵の無いリクエストは `/doc` も含めて 401。
- serve 経由では read も bash も聞かれずに通った（設定で `ask` にしている人は答え待ちで止まる。それを画面から答えられるようにしたのが #421）。

### 許可（#421 / #422）

- `GET /permission` に `directory` を渡さないと保留が 1 件あっても `[]` が返ることは実機で確認した。
- 保留は v1 の `GET /permission` にだけ出る（v2 の `/api/session/<id>/permission` は空で、逆に v2 の口で作った要求は v2 にしか出ない。1.18.30 で実測）。
- `metadata` のキーは実物が `filepath` で、`filePath` だけを見ていたころは待ちの文言に種類しか残らなかった。
- 時間で畳まないのは、「N 時間たったら」は当て推量で、端末で開いたまま人が席を外しているだけの待ちまで消すため。

### 使わない口（#400）

- 162 ある口から使うものだけ足していくと、「使わないと決めたもの」が忘れられて後から誰かが足すため、理由ごと残すことにした（表は screen.md の「返信と許可」）。
- `delivery` が v2 の `prompt` にしか無く、v1 の `prompt_async` には無いことは 1.18.30 の `/doc` で確認した。

## 新しいセッション

- Claude（#314）: 2.1.266 で実測。フックの `session_id` が `--session-id` で渡した UUID になり、同じ UUID の二度目は CLI が `already in use` で断る。
- Codex（#401）: 返る thread id がそのまま rollout のファイル名・`session_meta.session_id` になることは v0.154.0 で実測。

## claude --bg（#462）

実測（2.1.276〜278）で分かった 4 つがこの形を決めている。

- デーモンは起動した側の環境を継がない: `AGENT_FEED_DIR` を環境で渡しても record.py に届かず本物の置き場に書かれた。
- `--permission-prompt-tool` は使われない: MCP サーバは起動するが `approve` は呼ばれず TUI のダイアログで止まり、`claude agents` では `status: waiting`。
- `--session-id` は効かない。
- 生きている bg のセッションには `-p --resume` が断られ、`--bg --resume` は別のセッションに写す（止めたあとにフラグ無しで打つと同じ ID で起きるが、起動時の設定のまま）。

そのほか:

- 2026-09-24 に実測: `claude stop` は attach している端末を `Session … has exited.` でその場で閉じ、打ちかけも消える。これが「attach していれば止めない」理由。
- `ps` で素朴に `attach` を含む行を探すと、SAI 自身の `claude -p` の `--mcp-config` の中の `attachments` に当たった（実測）。そのため `claude` `attach` `<ID>` が続けて並ぶ行だけを数える。
- 2.1.278 の `claude agents` はバックグラウンドの行に `state` しか持たず（`status` も `pid` も無い）、2.1.276 は `status` = `busy` / `idle` / `waiting` だった。
- 返信のたびに `claude agents` を起こすと、端末に打ち込む経路より手前で 0.15〜0.20 秒増える。そのため覚えているものを先に見る。

## 預かり・steer

- #170: 長いターンの間フィードから何も送れないのを避けるため、端末に打ち込む経路は処理中でも通すことにした。
- #305: 別プロセスの経路で処理中に送った分を 409 で断る代わりに預かるようにした。前の返信が失敗していたら回さないのは、失敗したターンの続きを黙って積み上げないため。
- #404: `turn/steer` の形（`{ threadId, expectedTurnId, input }`）と `expectedTurnId` が本当に守られること（別のターンなら `expected active turn id X but found Y`、終わっていれば `no active turn to steer`）は v0.154.0 で実測。既定を預かりにしたのは、動いているターンに足すのは「次のターンとして回す」と別の意味で、足した分は取り消せない（走っているターンの筋がその場で変わる）ため。

## Claude の `-p` を止める・足す（#386）

- 前は Claude の `-p` には止める口が無く `400` だった（`-p` に SIGINT を送る案は「閉じないまま残るターン」を増やすだけなので採らなかった）。「今のターンに足す」も Codex だけだった。
- 使用量のための `--output-format` を `json` から `stream-json` に変えた（入力の口を開けるには出力も stream-json にする必要があり、`-p` で stream-json を出すには `--verbose` が要る）。
- 実機（2.1.285）で確かめたこと: 止めたターンでは `Stop` フックが鳴らず、プロセスは exit 1 で終わる（だから止めた返信は失敗にしない）。足した指示では `UserPromptSubmit` が鳴り、`Stop` の行の `user_text` は元の指示のまま。許可・質問の配線はこの入力の形でも今までどおり動いた。途中で stdin を閉じてもターンは `result: success` まで走った（引き取った子を止められない理由）。
- reply.log は 1 ターンで 100KB ほどに育つ（`--verbose` の stream-json）。
- 長寿命の 1 セッション 1 プロセスにはしない（`claude` は 1 本 約 350 MB で worktree が 17 ある）。
- stdout を pipe にしないのは、立て直したあとに引き取った子が書き込みで死ぬため（#387 と同じ理由）。

## 打ちかけと失敗の戻し

- #338: 確認から送り直すと `ReplyBox.submit()` を通らないので、前は送れているのに本文が入力欄に残り、打ちかけ（#306）にも保存されて画面を移っても再読み込みしても出てきた（そのまま Enter を押すと二重に送る）。
- #350: 戻すのを入力欄が空のときだけにしたのは、人がもう次を打ち始めていたら上書きしないため。非同期の失敗を自動で戻さないのは、2 分後に勝手に流し込むと、その間に打っていた本文と喧嘩するため。

## 許可モード

- #265: 見出しの `<select>` から入力欄のモデルの右へ移した。
- 「そのターン限り」は、フラグ付きで回したセッションをフラグ無しで再開すると元に戻ることを確かめた（`--model` と違う）。
- #272: `acceptEdits` で回っているターンの途中で素通しに変えると、そのターンは許可を聞き続けて「素通しにしたのに聞かれる」ように見えた。そのため起動したときのモードを `replying` に持つようにした。
- メタが素通しでも SAI が許可を自動で返さないのは、選んだ瞬間に起動済みのプロセスまで素通しになり、#253 の前提が広がるため。
- `bypassPermissions` でボタンを赤くするのは、そのセッションでは `isCrossOrigin()` が唯一の砦になるため（それ以外では「CLI が未許可のツールを拒否する」が二重目の歯止め）。
- 2.1.266 で実測: 許可は素通しになるが質問は素通しにならない（ツールの許可は `--permission-prompt-tool` を通らないが `AskUserQuestion` は通るので、質問のバブルはそのまま出る）。
- #271: 名前を英語にしたのは、Claude Code が端末の `Shift+Tab` で出す言い回し（`accept edits on` / `bypass permissions on` / `plan mode on`）に揃え、同じモードが端末と SAI で別の名前に見えないようにするため。UI 文言を日本語で書く方針の例外で、例外は名前だけ。

## モデル

- #394: `/api/model` の全件（手元で 93）ではなく `/config/providers` にしたのは、数の多さより、その人が実際に使えるものの方が当たるため。プロジェクト限定の provider が `directory` で現れ／消えることを実機で確かめた（サーバは homedir で動くので、渡さないと取りこぼす）。
- #282: 選択肢の名前を英語にしたのは隣の許可モード（#271）と揃えるため。言い回しは Claude Code のモデル選択から取った。未設定のボタンが許可モードと同じ `Default` になるのは意図的（どちらも CLI に任せる）。
- メニューと保存する値を正式名のままにしたのは、`claude-opus-5` と別名の `opus` がどちらも `opus` に見えてしまうため。

## 別のマシン（#114）

- 複数マシンの JSONL を集めていると（#24 / #113）、ここでは再開できないセッションが一覧に混ざる（CLI も履歴もあちら側）。
- #288: 前はサーバが別の `SAI_HOST` を見ていて、README の手順どおり `AGENT_FEED_HOST` だけ設定すると自分のセッションが「別のマシン」になり返信の口が消えた。
- `replyBlockedReason()` の第 2 引数に既定値を持たせないのは、持たせると渡し忘れが黙って「全部ローカル」になるため。`host` が空の行をリモートにしないのは、材料が無いのに返信を止めないため。
