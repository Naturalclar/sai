# server の経緯

なぜ今の形になったか（前はどうだったか・実測・レビューの指摘）。仕組みは [internals/server.md](../internals/server.md)。新しい経緯はこのファイルの該当する節に足す。

## 終わり方（shutdown）

- #296: 前は 2 回目の C-c でも同じ `close` を呼ぶだけで、連打しても何も起きなかった。いまは 2 回目はすぐ終わる。
- 実測では、ポーリングする keep-alive もアイドルの keep-alive も `close()` が自分で切って 3ms で終わり、抜けられないのは「リクエストを最後まで送っていない接続」（ブラウザの先読み・送信途中）だった。
- listen だけ消えて node が生き続けると、`/sync-main` が打った起動コマンドが foreground の pnpm に飲まれ、SAI が止まったままになる。これが「必ず終わる」にした理由。

### `opencode serve` を落とす・引き継ぐ（#457 / #440）

- 実測（2026-09-25）で、SAI が起こした `opencode serve` を落とさないと、ppid 1 の孤児になって走り続けた（立て直すたびに 1 本ずつ増える。保留中の許可もその中に残る）。一方 `codex app-server --stdio` は親が死ぬと stdin のパイプが閉じて自分で終わるので、触らないことにした。
- serve の出力を pipe のままにすると、SAI が落ちたあとに書いた瞬間に EPIPE で死ぬ。そのため `opencode-serve.log` に書かせる。
- 実機で、ターンの途中の C-c のあとも serve が生き残り、立て直した SAI が同じ serve を引き取って「止める」が効くこと、回していないときの C-c では落ちてファイルも消えることを確かめた。

- #683: `statusline.py` は `rate_limits` が来るたびにそのまま上書きしていたので、再開した古いセッションが持ち回っている期限切れの `rate_limits`（実測 25 回の描画のうち 3 回。戻る時刻は 1 か月以上前のものもあった）が 1 回来るだけで、取れていた割合が読む側に全部捨てられる中身に置き換わり、画面から消えていた。それで書く側でも期限切れの窓を落とし、置いてある記録より古い `ts` では上書きしないようにした。`ts` は書いた時刻なので、**まだ期限内の古い値**（同じ窓の少し前の割合）を持ち回る描画は区別できず、今までどおり上書きする。置いてある記録を残すのを「`ts` が 5 分以内の先で、生きている窓がある」ときに絞ったのはレビューの指摘で、先の `ts` を無条件に残すと、時計の狂ったマシンが書いた記録がその時刻が来るまで居座り、割合が止まったまま期限切れで消える（直す前は次の描画で自然に戻っていた）。窓ごとに新しいほうを残す（マージ）のは、別の描画の窓を混ぜた記録になるので入れていない。
- #689: `/usage` と突き合わせると、週が実際 47% のところ SAI は 37% だった（2026-10-05）。`rate_limits` はそのセッションが最後に受け取ったものを持ち回るので、しばらく API を呼んでいないセッションが描画すると古い値に新しい `ts` が付く（37% を書いたセッションの transcript は 24 分前で止まっていた）。それで同じ窓なら高いほうを残し、変わらなければ書かない（`ts` を描画した時刻から、割合が最後に変わった時刻にした）。#683 で入れなかった窓ごとのマージもここで入れた。高いほうを残すだけだと、枠が途中でリセットされたとき古い高い値が窓の終わりまで残るので、24 時間変わっていない窓は低い値でも置き直す（はじめは記録全体の `ts` で見ていたが、レビューで、5 時間の窓が動いている間は `ts` が進み続けて週の逃げ道が開かないこと、古い記録に 5 時間だけの描画が来ると週が消えることを指摘され、窓ごとの `changed_at` にした）。**新しい値がそもそも来ないことは直っていない**: 37% が書かれてから 40 分近く、複数のセッションが動いていても記録は 1 回も変わらなかった（`rate_limits` の載った描画がほとんど来ない。#683 の実測では 25 回中 5 回）。
- #694: #684・#690 のあとも、画面の割合は実際より遅れていた（2026-10-05 の 11:27 ごろ、`/usage` は週 47%・5 時間 12%、SAI は 10:57 に書かれた週 37% だけで、記録は 11:49 まで変わらなかった）。`rate_limits` の載った描画がほとんど来ないのが主因だが、どういう描画に載るのかが分かっていない。それで先に調べる口として、`AGENT_FEED_DEBUG=1` のときだけ入力の要点を `statusline-debug.log` に残すようにした。手元のラッパーで `tee` する案は、入力をそのまま残すと cwd や transcript のパスまで溜まるのと、ほかの人のマシンで同じ調べ方ができないので採っていない。

- 割合が古いことを画面に出すようにした（#694）。2026-10-05 に記録を取って分かったこと: 動いていたのは SAI から回した `claude -p` が 4 つと端末の TUI が 25（24 が idle）で、20 分のあいだステータスラインは 1 回も呼ばれなかった（`-p` は描かない）。`usage-claude.json` は 10/5 10:57 の値（週 37% だけ）のまま 27 時間以上止まり、画面は「10:57 時点」とだけ出していたので、きのうの値が今日の値に見えていた。来ないこと自体は `statusline.py` からは直せないので、古いと分かるようにする。閾値の 30 分は、同じ日の実測（並行して回していた 30 分で週が 37% → 47%）と、色の境目の幅（80% と 95% の間の 15 ポイント）から選んだ。端末で使っていれば発言のたびに届くので、ふつうは付かない。
- 同じ PR のレビュー（#719）で出たこと。(1) 使用量は開いたとき・戻ったとき・パネルを開いたときしか取り直さないので、表に出したままのタブでは「取ってきた時刻」が進まず、何時間たっても印が付かなかった → 表に出ているあいだは 5 分おきに取り直す。(2) `usage-claude.json` の `ts` は「割合が最後に変わった時刻」（#689）なので、届いているが変わっていない値（上限中の 100%・軽い利用）にも印が付く。いったん `statusline.py` に「最後に届いた時刻」（`seen`）を足したが、2 回目のレビューで、API を叩いていない描き直し（許可モードの切り替えなど）でも同じ値が来て `seen` が進み、止まっている値が「いま」に見えると分かった（記録でも、API の時間が進んでいない描画が続けて来ていた）。区別が付くまでは `seen` を持たず、**測るのは「変わってから」のまま、文言を「◯ 前から変わっていません」にして言い切らない**ことにした。区別する案（そのセッションの `cost.total_api_duration_ms` が進んだ描画だけを数える）は、記録が溜まってから決める。

- 「最新の値を出したい」（#694 の続き。2026-10-06）。ステータスラインの口は端末でしか動かないので、別の出どころを探し直した。`~/.claude/` の下と transcript には無かった（10/5 に確認）が、**SAI が起こした `claude -p` の出力そのもの**に載っていた: stream-json（#386 で入力の口のために使い始めた）は API の応答ごとに `rate_limit_event` を出し、`unifiedWindows` に 5 時間と週の `utilization` と `resetsAt` が入っている。reply.log の末尾 30 MB に 252 件あり、その時点の値は 5 時間 2%・週 61%（画面は 27 時間前の週 37% のままだった）。OAuth の API を叩く・`claude -p` を定期的に回す、は #694 の「やらないこと」のままで、読むのは SAI が頼まれて回した返信の出力だけ。ステータスラインの値と混ぜるときに単純な「新しいほうを丸ごと」にしなかったのは、古い値を持ち回っている端末があとから書いた低い値に負けないため。最初は `statusline.py` と同じ「窓ごとに、同じ窓なら高いほう」にしたが、レビュー（#723）で 3 つ出た: 枠が途中でリセットされると古い高い値が窓の終わりまで残る・返信に無い窓を古いステータスラインから持ってきて「いま」として出す・端数の違いだけで古い時刻になる。2 つは時刻の意味が違う（返信は届いた時刻、ステータスラインは変わった時刻）ので対称に扱うのをやめ、**返信が新しければ丸ごと、ステータスラインが新しいときだけ窓ごと**にした。同じレビューで、ターンの終わりに出力を頭から渡し直して古い知らせに「いま」と刻んでいた点・値が変わるたびに同期で書いていた点・マシンごとに分けていなかった点も直した。

## 画像の軽い版（local/thumbnails.ts）

- #589: 枠は 96px / 最大 320px なのに `<img src>` が元の画像で、Codex の生成画像（1 枚 2MB 前後）が 6 枚の短いセッションを開くと 12.2MB 読み、10Mbps / 40ms に絞った模擬で 9.4 秒かかっていた。`loading="lazy"` は効いていたが、発言が少ないと全部がしきい値の内側に入る。
- `server/` に依存を足さない（Node に画像のコーデックは無い）ので、macOS 付属の `sips` を PATH から呼ぶ。`sips` に元のファイルのパスを渡さず、読み終えたバイト列を置き場に書き直して渡すのは、transcript の画像がファイルでない（base64）のと、読む条件（cwd の中・中身で種類・上限）を 1 か所に保つため。
- 大きさとしきい値は実測（10/1、負荷平均 30 前後のマシン）で決めた:
  - 長辺 512px・品質 75 の JPEG: Codex の生成画像（1024×1536、1.9〜2.0MB）が 48〜56KB、1254px の 0.9MB が 24KB。1 枚 0.1〜0.2 秒（初回だけ。2 回目は置き場から 1〜13ms）。2MB の生成画像は 384px（品質 70〜80）でも 45〜52KB と大差なく、本文の中の 320px 枠が粗くなるので 512px の 1 種類にした。
  - PNG のまま 512px にすると 374KB で軽くならない。透過のある PNG（Codex の生成画像 12 枚のうち RGBA が一部）は 512px だと 124〜290KB、384px で 75〜175KB なので 384px にした。`sips` の JPEG 変換は透けた所を白で埋める（黒ではない。実測）が、アイコンの白い箱になるので PNG のまま縮める。
  - しきい値 200KB: 記録の画像 306 枚の中央値が 121KB・p90 が 324KB で、100KB 未満が 131 枚。小さい画像は縮める時間のほうが高いので元のまま返す。
- 作る時機は「最初に求められたとき」。一覧（`/gallery`）を返すときに裏で作り始めると、開かないセッションの画像まで縮めることになる。
- 縮められないときに元を返さず `503` にしたのは、`sips` の無いマシン（Linux）で結局 12MB を読むことになるため（#589 の案 2。押すまで読まない）。`GalleryItem` に `bytes` を足す案もあったが、本文の画像（`MarkdownImage`）と添付は一覧を通らないので、4 つの口で同じ形になる HEAD の見分けにした。
- #593 のレビュー: 画面の見分けの HEAD がもう一度 `sips` を回していた（締切で落ちたものは HEAD も 15 秒待ち、そこで出来ると 200 が「表示できません」になった）。それで縮められなかった中身を 10 分覚え、画面は 200 なら 1 回だけ読み直す。また `sips -Z` は小さい画像を引き伸ばす（300×300・270KB の PNG が 512px・226KB になった）ので、見出しの縦横が目標以下なら引き伸ばさない。

- #709: 200KB 以上の横に細長い画像（帯）が、画面で広がらなかった。画面（#702）は帯を高さ 80px まで広げるが、広げる上限は読み込んだ絵の幅で、読み込むのは軽い版（長辺 512px）なので、2880×200（344KB）の表のスクリーンショットは 512×37 で止まり字が読めなかった（一時の記録と headless で実測。携帯の幅 390px では 294×22 のままで、こちらは絵が粗いだけ）。
  - 案 1（軽い版の応答で元の大きさを伝え、画面が上限を元で決める）は採らなかった: `<img>` は応答のヘッダを読めないので画像ごとに 1 往復増え、上限を広げても絵は軽い版を引き伸ばすだけで字は読めない。帯のときだけ元を読むなら 344KB で、軽い版の狙い（#589）から外れる。
  - 案 2（帯のときだけ軽い版の長辺を大きくする）にした。画面は変えなくてよい（軽い版の幅が上限を超えるので、上限は縦横比 × 80px になる）。同じ画像の実測: 長辺 512px で 11KB、短辺 80px（1152px）で 52KB、短辺 120px（1728px）で 98KB、短辺 160px（2304px）で 155KB、元は 344KB。高い画素密度の画面でも字が読め、元の 3 割に収まる短辺 120px にした（帯 1 枚あたり 87KB 増える）。
  - 透過のある帯は PNG のまま縮めるので、2880×200 を長辺 2304px にすると 534KB で元より重く、元のまま返る（`result()` の「縮めても重ければ元」）。
