## マージのあとの `/sync-main` を `/merge` が呼ぶ（#580）

- 9/2〜10/1 でマージした PR は 288 本、人が打った `/sync-main` の類は 76 回。マージしても main worktree は古いままなので、画面に「ビルドが古い」が出て、人がそれを見て別のセッションへ打ちに行っていた。`/merge` の後始末に入れた（バナーから回す案は入れていない）。
- 2 つのセッションがほぼ同時にマージすると `/sync-main` が 2 本走る。ff-only の merge は重なっても安全だが、立て直しが重なると起動コマンドが飲まれる（#296）ので、後から来た方が譲る lock を置いた。
- **「譲る = 何もしないで終わる」にはしなかった。** 先の方が fetch したあとに後の方のマージが入ると、先の方は 1 つ前までしか進めない。後の方は待ってから普段の手順をそのまま回す（最新なら手順の側が何もしない）。一時リポジトリでの模擬（立て直しは 3 秒の待ちで代えた）: lock なしで同時に 2 本 → 立て直しが 2 回重なる。lock ありで同時に 2 本 → 1 回。先の方の fetch のあとに次のコミットが入る → 先の方が 1 回、後の方がもう 1 回で、最後は最新。
- lock を main worktree の中ではなく git の共通ディレクトリに置いたのは、`/sync-main` 自身が「`git status` が空でなければ止める」ため（追跡外のファイルを置くと自分で自分を止める）。
- lock の持ち主をプロセス（pid）で見分けないのは、スキルの手順が Bash の呼び出しごとに別のシェルになるため。代わりに取った時刻で古さを見る（待つ上限 480 秒 < 引き取り 900 秒。待ち切れなかった側は奪わずに報告する）。
