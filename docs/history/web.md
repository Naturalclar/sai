# web（画面）の経緯

なぜ今の形になったか（前はどうだったか・実測・レビューの指摘）。仕組みは [internals/web.md](../internals/web.md)。新しい経緯はこのファイルの該当する節に足す。

## 要対応

### 「終わって次を待っているだけ」を `done` に分けた（#438）

- Claude はターンが終わって 60 秒放置されると `idle_prompt` の `Notification` を鳴らすので、これを待ちとして数えると返信が 1 回終わるたびに要対応が 1 件増える。
- 実データ 15 日ぶんで、待ちの行 331 件のうち 137 件が `入力待ち`、うち 134 件は同じセッションのターン完了の直後だった。
- tmux のペインがあるものは `WaitingSettle` が入力欄を見て偶然畳んでいたが、ペインの無い端末では次の入力まで残っていた。

### 最後の行がターン完了なら `done` にする（#513）

- `idle_prompt` は端末の TUI の Claude しか鳴らさず、`-p`・Codex・OpenCode の終わったセッションが出ていなかった。
- 時刻 `end === last_turn_ts` で比べる案は採らなかった: 行の `ts` は秒までなので、同じ秒に届いた次の入力や `/clear` を見分けられない。集計の `last_kind` で見る。

### 判定を `shared/` へ移した（#340）

- サーバからも同じ判定を呼べるようにするため、`web/src/` から `shared/todoItems.ts` へ移した。

## コンポーネント

### 静的な兄弟に同じ `key` を付けない（#264）

- 見出しの 4 つが `key={s.id}` を共有していて、3 秒のポーリングごとに +3 で「表示名なし」と許可モードの列が積み上がった。
- 位置で対応が付いているうちは表に出ず、`RepoLink` が `null` を返して並びが崩れたときに初めて出た。本番ビルドは React の重複 `key` の警告が落ちているのでコンソールにも何も出なかった。

## 返答の一部の引用（#604）

- T3 Code（pingdotgg/t3code）の「Cite in composer」を見て足した。返信欄に「足す」口は差分・PR の行コメント（#511 / #526）と `/manager` の案（#565）だけで、返答の文そのものは引用できなかった。このリポジトリの返答は「決めてほしいこと」が箇条書きで 3〜5 個並ぶ形が多く、1 つずつ答える場面が多い。
- 決めたこと: 引用は**ただの `> 引用`**（時刻は添えない。エージェントは自分の直前の返答を覚えている）。**携帯も同じボタンを選択の下に出す**（iOS の OS のメニューは選択の上に出るので重ならない見込み。実機では未確認）。箇条書きの項目ごとの印は、使ってみて要ると分かってから。

## セッション画面

### 直近 7 日だけ描く（#477）

- 行の多いセッション（手元で 1045 行、DOM 2.3 万要素）は 3 秒のポーリングのたびにチャット全体を描き直し、CPU を 6 倍遅くした計測で打鍵が最大 170ms 止まっていた。直近 7 日に絞ると 176 行・DOM 5 千・最大 12ms。
- 7 日を「いま」から数える案は採らなかった: しばらく触っていないセッションが空で開き、7 日以上前に止まった待ちのバブルまで消える。
- 前の行を足したときの位置合わせをブラウザのスクロールアンカーに任せなかったのは、Safari に無く、先頭で押したときは Chrome でも効かないため。

### 発言を `ts` と側で名指しする（#503）

- `ts` だけで名指ししていた前は、検索の飛び先で自分の入力と返答の両方が光っていた。
- `Utterance.key` は位置（`index`）を含むので 7 日の窓が動くとずれるため、リンクには使わない。

### 最下部追従を高さで見る（#344）

- 高さで見ていなかったころは、最下部から 40px 以内にいる間は行が 1 つも増えていなくても 3 秒ごとに `scrollTop = scrollHeight` が走り、直前の発言を読み返せなかった（`SessionView` の `trailer` は常にあるのでセッション画面は必ず、フィードは処理中・承認待ち・預かりがあるときだけ起きていた）。

### 箱が縮んだときも送り直す（#544）

- 差分ボタンが出たぶん `.reply` の `margin-top` を広げる（#351）ので、最下部まで送ったあとで箱が 32px 縮む。中身の高さは変わらないので `followsBottom()` は送らず、最後の発言の下がボタンの陰に隠れたまま止まっていた。
- 実機の headless で、直す前は最下部まで 32px、直したあとは 0 を確かめた。

### アーカイブ後も返信が続いているのを知らせる（#583）

- アーカイブ済みかは `archived_at >= end` で決めるので、行が増えると黙って一覧に戻る。実データで、9/4 にアーカイブしたセッションがそのあと 143 ターン回っていて、同じ worktree・同じ表示名の新しいセッション（9/25〜）と見分けが付かなかった（89 セッション中 2 本）。
- 返信は止めない・一覧に戻すのもやめない（見えなくなる方が害が大きい）。送る前の確認も挟まない（意図して使い続けている人には毎回邪魔になる）。1 行の知らせと［このまま使う］にした。
- サーバには新しいフィールドを足していない（`meta.archived_at` と `archived` は既に応答に載っている）。

## Markdown と画像

### 本文の画像の参照（#321）

- `[名前](パス)` の形も画像として扱うのは Codex がこの形で出すため。実データの画像の参照はこれだけだった。

### 自分の入力の画像も配る（#504）

- 前は返答の画像だけを配っていた。自分の入力（`user_text`）の画像の参照と地の文の画像のパスも表に入れた。

### 画像を出てきた発言のバブルの下に出す（#504 / #507）

- 前はセッション全体の画像を会話の末尾に 1 行で並べていて、どの発言の画像か分からなかった。

### Codex の生成画像が出なかった（#575）

- Codex の画像生成で作った画像は、返答の本文には「生成しました。」だけでパスが載らず、フックの payload にも無い（codex 0.154 で実測。手がかりは rollout の `item_completed` だけ）。
- 本文の画像を配る口（`images.ts`）は行の `cwd` の中しか配らないので、本文に保存先が書かれていても `~/.codex` の中は出なかった。そのため rollout から拾う別の口（`CodexImages`）にした。

### transcript の画像を待ちの行に付けない（#508 のレビュー）

- 待ちのバブルには画像を出さないので、待ちの行に付けると、Read のあとに許可を聞いたターンで画像が消えた。

### ピンチで拡大している間はスワイプで送らない（#510 のレビュー）

- 拡大中も送っていると、拡大した広いスクリーンショットの右側を読めなくなる。`touch-action: auto` に戻して横スクロールに任せる。

### GFM の表（#328）

- 実データで返答の 6.5% に表があった。

### 長い本文を開いた状態で始める（#365 / #369）

- `.clamped` は CSS で隠しているだけなので費用は変わらず、実測でフィードの高さが 23,295 → 34,973px になるだけだった。
- #610 のレビュー: 戻ってきた印（#583）は `archived_at` より後に行が増えれば出ていたので、アーカイブしたあと端末を閉じただけ（`SessionEnd` の行）でも「返信が続いています」と出た。最後の行が終わりの行で、アーカイブより後に終わったターンが無ければ出さない。
